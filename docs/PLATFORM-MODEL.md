# Платформа для многих специалистов — модель (спецификация под реализацию)

> Статус: **черновик на согласование с владельцем (2026-06-06, уточнён).** Код ещё НЕ менялся.
> Цель — вырастить из готового [кабинета нутрициолога](../cabinet/index.html) платформу, где
> ИП (Интерпретатор) становится инструментом для разных профильных специалистов вокруг
> направления **пред-менопауза / андропауза**.
>
> Принцип: **ничего готового не ломаем.** Текущий нутрициолог = «специалист №1», все её
> клиенты остаются при ней, EXPERT/ELITE-воронка работает как сейчас. Платформа вырастает
> шагами, каждый проверяемый на живом.
>
> **Ядро платформы — КАБИНЕТ.** Всё остальное к нему пристёгнуто: **PRO** = топливо (данные
> ИП + биометрия носимых текут в кабинет по коду), **EX/EL** = не отдельная технология, а
> **включённые функции кабинета** поверх PRO (анкета → ИИ-черновик → PDF → Zoom → перевод),
> **CO (основатель) и СМ (специалисты Мира)** = два типа операторов *одного и того же* кабинета,
> **клиент** привязывается к кабинету по `?ref` + согласие. Экономика держится на этом: мы
> **сдаём кабинет в аренду** специалисту (€39/мес) + продаём PRO клиенту; EX/EL как отдельный
> товар не строим. Развитие платформы = развитие кабинета (витрина, мост перевода, профильные
> виды — слои на кабинете, не отдельные продукты). Убери кабинет — рассыпается всё.
>
> Базовая модель кабинета (откуда растём): [`docs/CABINET-MODEL.md`](CABINET-MODEL.md).

## 0. Замысел (зачем платформа)

ИП — **инструмент в руках чужого врача.** Смежные специалисты (гинеколог, эндокринолог,
андролог и т.п.), чья работа пересекается с нашим направлением, подключаются к платформе:

1. Специалист **рекомендует своему клиенту гаджет** (носимое устройство; часть клиентов уже носит).
2. Клиент оформляет **месячную подписку на ИП** (тариф PRO).
3. Специалист получает **ИП-помощника для ведения**: видит биометрию клиента с устройства и
   ИИ-разборы — и управляет своим клиентом из кабинета.

Ключевое разделение ролей: **живой эксперт для клиента — это его собственный доктор**, а
платформа даёт инструмент (ИП + ИИ). Поэтому клиентам внешних специалистов достаточно PRO —
без нашего ведения. EXPERT/ELITE (с ведением *нашего* нутрициолога) остаются **личной воронкой
основателя**: иначе на одном клиенте окажутся два эксперта.

Терминология: **«профильный специалист»**, без личных имён в продукте
(см. memory `feedback_no_personal_names_in_ip`).

## 1. Две модели клиента (главная развилка)

| | A. Клиент основателя | B. Пациент внешнего специалиста |
|---|---|---|
| Что купил | EXPERT / ELITE на сайте (Hotmart) | **подписку на приложение ИП** (App Store / Google Play) |
| Кто ведёт человеком | наш нутрициолог (PDF/Zoom) | его собственный врач (гинеколог и т.п.) |
| Роль ИП | полное ведение + ИИ + нутрициолог | инструмент: ИП + ИИ-разбор + носимые |
| Деньги пациента идут | нам (Hotmart) | в магазин (Apple/Google); **специалисту — отдельно, по его расценкам, мимо нас** |
| Привязан к | специалисту №1 (основатель) | **своему специалисту — по его коду + согласие** (см. §3) |
| Карточка в кабинете | да (как сейчас) | **да — НОВОЕ** (см. §3) |

> **Что меняется в правиле кабинета.** Сейчас: «в базу только EXPERT/ELITE + сайт-ведение;
> PRO/VIO — НЕ заводим» (см. `CABINET-MODEL.md` §2, memory `project_ip_tariffs`). В платформе
> **пациент специалиста заводит карточку — когда подключается к специалисту по его коду.**
> Тарифную страницу (PRO/EXPERT/ELITE, Hotmart) пациент специалиста НЕ видит — это прямая
> воронка основателя. VIO и «прямой» self-serve без специалиста — карточку не заводят.

## 2. Специалист (новая сущность)

Запись в новой таблице `specialists`:

| Поле | Что это |
|---|---|
| `id` | уникальный ключ специалиста |
| `name` | имя (для интерфейса) |
| `login` / `pass_hash` | вход (пароль хэшем, не в открытом виде) |
| `lang` | **рабочий язык** — язык интерфейса и ИИ-черновика специалиста |
| `specialty` | профиль: `gynecologist` / `endocrinologist` / `nutritionist` / … |
| `role` | `specialist` (обычный) / `owner` (владелец платформы) |
| `ref_code` | **код специалиста** («код клиники») — пациент вводит его в приложении, чтобы подключиться (§3) |
| `access_status` | **`active` / `lapsed`** — оплачена ли абонентская плата за доступ (§5) |
| `access_paid_until` | до какой даты оплачен доступ |
| `status` | `active` / `disabled` |
| `created_at` | дата заведения |

**Миграция без потерь:** текущий нутрициолог = `id=1`, `specialty=nutritionist`, `lang=ru`,
`role=owner`. Вход через `CABINET_PASS` работает в переходный период.

## 3. Привязка клиента к специалисту

К таблице `clients` добавляется колонка `specialist_id` — чей это клиент (сделано на Шаге 1).
**Бэкфилл:** всем нынешним клиентам → `specialist_id=1` (ничего не переезжает).

### Алгоритм «специалист заводит пациента» (подтверждён владельцем 2026-06-06)

Исходное условие: у пациента **уже куплена подписка на приложение ИП** (через App Store /
Google Play), он им пользуется. Деньги за приложение идут в магазин; со специалистом пациент
рассчитывается отдельно, по его расценкам, **мимо нашей платформы.** Задача алгоритма — связать
этого пациента со специалистом так, чтобы данные и разборы текли в кабинет специалиста.

Механизм — **код специалиста + согласие пациента** (переиспользуем `ref_code` из Шага 1 и
уже работающий ингест ИП по коду `cabinetIngestIpAnalysis`):

1. У каждого специалиста есть постоянный **код** (`specialists.ref_code`, «код клиники»).
2. Пациент в приложении ИП открывает «Мой специалист» → вводит этот код.
3. Приложение показывает, кто запрашивает, и спрашивает **согласие на передачу данных о
   здоровье** → пациент жмёт «Поделиться». (юридически важный шаг согласия)
4. В этот момент: в кабинете специалиста **автоматически появляется карточка пациента**
   (`specialist_id` = этот специалист), а **каждый последующий ИП-разбор + биометрия носимого
   этого пациента сами текут в карточку** — по уже существующему механизму ингеста по коду.
5. **Отвязка:** пациент в любой момент жмёт «Перестать делиться» → поток прекращается.

Опционально (позже): специалист сам пред-создаёт карточку (имя/email) и шлёт пациенту
персональный код-приглашение — для случаев, когда удобнее инициировать со стороны специалиста.

**Один специалист на пациента.** Случай «несколько специалистов на одном пациенте»
(напр. гинеколог + психолог) — пока не делаем, отложенный край.

## 4. Вход и видимость

- **`/cabinet-auth`** вместо одного `CABINET_PASS` проверяет логин+пароль по `specialists`.
  Токен запоминает, КТО вошёл (`specialist_id`). Доступ закрыт, если `access_status='lapsed'`
  или `status='disabled'`.
- **`/cabinet/clients`** возвращает только клиентов вошедшего (`WHERE specialist_id=<свой>`);
  роль `owner` — всех.
- Все `/cabinet/*` проверяют, что открываемый клиент принадлежит вошедшему (нельзя открыть
  чужого по коду).
- Переходный период: `CABINET_PASS` остаётся как вход «владельца №1» — день переключения
  ничего не ломает.

## 5. Монетизация (подтверждено владельцем 2026-06-06)

Три раздельных денежных потока, **через нашу платформу проходит только один — абонплата
специалиста:**

- **Пациент → магазин:** платит за **подписку на приложение ИП** в App Store / Google Play.
  Эти деньги идут Apple/Google (мы — через встроенную кассу). **Через нашу платформу платежей
  пациента нет.**
- **Пациент → специалист:** за ведение платит специалисту напрямую, по его расценкам, на месте —
  **мимо нас.** Платформа этих денег не видит и не считает.
- **Специалист → нам:** **абонентская плата за доступ к платформе** (повторяющийся платёж) —
  единственный наш доход с этого канала. **Размер (подтверждено владельцем 2026-06-07): €39/мес
  или €390/год (2 месяца в подарок), первый месяц бесплатно, безлимит пациентов на старте.**
  Ступени по числу пациентов — позже, по данным. Заплатил → `access_status='active'`, сдвигается
  `access_paid_until`. Не заплатил → по истечении ставим `lapsed` → вход в кабинет закрыт
  (данные пациентов сохраняются, не удаляются).
- Технически абонплата специалиста — отдельный платёжный продукт (Hotmart-подписка или иной),
  webhook обновляет `access_status` / `access_paid_until`. Провайдер — открытый вопрос §9.

> Воронка основателя (EXPERT/ELITE через Hotmart на сайте) — отдельный поток «пациент → нам»,
> не связан с каналом внешних специалистов.

## 6. Мост перевода («кнопка переводов»)

Переводим ТОЛЬКО на стыке языков. Движок — тот же ИИ (Claude); автоперевод в канале ведения
уже работает (memory `project_vedenie_channel_target`).

| Где | Что | Как |
|---|---|---|
| Вкладка «Анкета» | ответы клиента | кнопка **«Перевести»** → на язык специалиста (`specialists.lang`) |
| Переписка, входящие | сообщение клиента | кнопка **«Перевести»** на язык специалиста |
| ИИ-черновик ответа | генерируется на языке специалиста (не жёстко русский) | язык вошедшего подставляется в промпт `/cabinet/ai-draft` |
| Отправка клиенту | готовый текст специалиста | **авто-перевод на язык клиента** (`clients.lang`) перед отправкой; совпали — без перевода |

ИИ по-прежнему НЕ пишет клиенту сам — готовит черновик, отправляет специалист. Оригинал
сохраняется рядом с переводом.

> Пока специалист один и говорит на ru/uk — ИИ-черновик намеренно на русском (решение владельца
> 2026-06-06). Язык черновика = «язык специалиста» включается, когда появятся специалисты с
> другими языками.

## 10. Онлайн-модель (специалист ведёт удалённо, как основатель в EXPERT/ELITE)

Разделы §1–9 описывают **офлайн-модель**: специалист приводит СВОИХ пациентов, деньги
пациента идут мимо нас (магазин + расчёт со специалистом на месте), мы — «только инструмент»
и берём с него аренду. **Онлайн-модель** — второй сценарий того же канала внешних
специалистов, отличается тем, что **пациент здесь полноценно наш клиент.**

### Суть

Специалист работает удалённо «по миру» — так же, как основатель ведёт EXPERT/ELITE, но
ведёт его **внешний специалист**, а пациент сидит на тарифе **PRO**. Здесь перевод и 12
языков становятся ядром, а не краем (специалист и пациент часто на разных языках).

### Денежные потоки (оба — через нас)

| Кто | За что | Куда идут деньги |
|---|---|---|
| **Пациент → нам** | тариф **PRO** (инструмент ИП + ИИ-разбор + носимые) | наша касса: IAP в приложении (~15% магазину) **или** код с сайта через Hotmart (0% магазину) — путь PRO см. [`MOBILE-APP-MODEL.md` §2](MOBILE-APP-MODEL.md) и открытый вопрос там |
| **Специалист → нам** | **аренда** = B2B-абонплата за доступ к платформе/кабинету | наша касса (Hotmart/иное), та же, что в §5 и §2 (`access_status`/`access_paid_until`) |
| **Пациент → специалисту** | ведение/консультации | **по расценкам специалиста, мимо нас** — по аналогии с офлайн §5 (предложено, подтвердить — см. ниже) |

Итог: с одной пары «пациент + специалист» у нас **два дохода** — PRO с пациента и аренда со
специалиста. Это и есть отличие от офлайн (где с пациента мы не берём ничего) и от воронки
основателя (где пациент на EXPERT/ELITE, а ведёт его сам основатель, без аренды).

### Что переиспользуем (нового механизма не нужно)

- **PRO** как поток с пациента — уже описан ([`MOBILE-APP-MODEL.md` §2](MOBILE-APP-MODEL.md)).
- **Аренда специалиста** — это абонплата из §5 / §2 (`/specialist-access-webhook`).
- **Привязка** пациента к специалисту — код специалиста + согласие из §3 (`/specialist/connect`).
- **Мост перевода** из §6 — здесь становится основным рабочим инструментом.

### EXPERT/ELITE-ведение силами специалиста

EXPERT/ELITE — это **не отдельная технология, а PRO + слой человеческого ведения:**
- **PRO** = инструмент (ИП + ИИ-разбор + носимые), деньги пациента нам.
- **EXPERT** = PRO + **Анкета** + ведение человеком (разбор анкеты → ИИ-черновик → правка
  специалистом → PDF пациенту).
- **ELITE** = EXPERT + Zoom-сессии.

**Анкета входит в EXPERT И ELITE** (в PRO её нет). Весь слой ведения (вкладка Анкета,
входящие, ИИ-черновик, генерация PDF, карточка в TG, запись через Cal.com, мост перевода)
**уже встроен в кабинет и одинаков для всех специалистов** — кабинет строился так, чтобы любой
специалист работал «как специалист №1». Поэтому, как только пациент-на-PRO подключился по
коду+согласию (§3), специалист ведёт его тем же набором инструментов, что основатель в
EXPERT/ELITE. Нового механизма не нужно — отличается только упаковка и кто берёт деньги за
ведение (см. «Доход специалиста» ниже). Анкету пациенту-на-PRO специалист отправляет ссылкой —
форма уже есть и переведена на 12 языков (`book/anketa`).

**Специалист EXPERT/ELITE не перепродаёт — он ими ПОЛЬЗУЕТСЯ.** «EXPERT/ELITE-уровень» для его
пациента = не покупка нашего тарифа, а **включение функций кабинета** (анкета-ссылка + Cal.com-бронь)
поверх PRO, по цене специалиста, мимо нас. Вариант «специалист продаёт НАШИ EXPERT/ELITE с
revenue-share» отклонён владельцем (тяжёлая ветка: посредник, выплаты, возвраты).

**Три раздельных продукта — что во что входит:**

| Продукт | Кто платит | Что это |
|---|---|---|
| **ИП (PRO)** | пациент → нам | инструмент-движок: ИП + ИИ-разбор + носимые. Данные, с которыми работают |
| **Кабинет** | специалист → нам (аренда) | **весь функционал кабинета**: анкета, ИИ-черновик, PDF, Zoom, переписка, перевод, карточки (= EXPERT/ELITE-уровень ведения) |
| **Сайт VIA-L** | — | наша воронка под EXPERT/ELITE основателя; специалисту **НЕ достаётся** — своих клиентов он приводит сам (канал 1) |

Аренда специалиста покупает **полный функционал Кабинета, но НЕ сайт VIA-L и НЕ владение ИП.**
ИП пациент покупает отдельно как PRO. Так разведены B2B-продукт (кабинет, со специалиста),
B2C-продукт (ИП/PRO, с пациента) и наш собственный маркетинг-канал (сайт).

**Расцепить Анкету от покупки.** Сейчас анкета выдаётся по коду после покупки EXPERT/ELITE на
сайте (§18.11). Для онлайн-канала анкету можно отправить **любому привязанному PRO-пациенту** —
на усмотрение специалиста, без отдельной покупки. Это и есть техническая доработка под вариант 2.

### Откуда у онлайн-специалиста клиент

В Модели 1 (лёгкой) маркетплейса с платным подбором НЕТ. Источника два:

1. **Главный — специалист приводит сам (работает уже сейчас).** Своя аудитория (Instagram,
   блог, сайт клиники, сарафан, текущие пациенты) → одна ссылка «купи PRO + введи мой код».
   Специалист = маркетинг, мы = инструмент за аренду. Это и есть «онлайн как офлайн, только
   удалённо». Механизм код+согласие (§3) для этого готов.
2. **Бонус — наша витрина (поздний этап, не на старте).** Часть людей покупает PRO через нашу
   воронку (бесплатный ИП / сайт), но своего врача не имеет. Для них — каталог специалистов в
   приложении (имя, профиль, язык, краткое описание, цена-ориентир, кнопка «бесплатное знакомство
   15 мин» через Cal.com). **Пациент выбирает сам** (мы не назначаем, лиды не «продаём») →
   срабатывает тот же код+согласие. **Денег через нас нет — это только discovery.** Это и есть
   ценность аренды: «плати аренду → получаешь наших PRO-клиентов». Цена бонус-канала —
   минимальный слой доверия: **верификация диплома специалиста + отзывы/рейтинг.**

**Решение:** стартуем без витрины (канал 1 обязателен и готов); витрина + верификация/рейтинги —
отдельный поздний этап, чтобы не тащить доверительную инфраструктуру в день один.

### Воронка канала 1 (специалист приводит сам)

**Рабочая единица = пациент на PRO + привязка к специалисту.** Оба факта обязательны, **порядок
любой** — что раньше (оплата PRO или ввод кода), неважно.

- **PRO — это рабочее вещество, а не «глубина для апселла».** Без PRO в кабинет не течёт ничего
  (ни ИП-разборов, ни биометрии носимых) → специалисту нечего анализировать. Поэтому покупка PRO
  пациентом — обязательное условие связки, а не опция.
- **Экономика замыкается сама.** Специалист платит аренду именно потому, что его пациенты на PRO
  кормят кабинет данными. Нет PRO → кабинет пуст → аренда бессмысленна. Аренда и PRO держат друг
  друга — искусственно «заставлять» покупать PRO не нужно.
- **Гейтить привязку оплатой не нужно — пустой кабинет сам себе гейт.** Без PRO специалист просто
  ничего не видит и сам доведёт пациента до покупки. Привязку (код+согласие §3) оплатой не блокируем.
- **Одна реф-ссылка** ведёт к обоим действиям: код специалиста запоминается (localStorage/deep-link)
  и применяется, когда бы привязка ни случилась; PRO покупается когда удобно (IAP/код с сайта).
- **На карточке пациента — индикатор PRO / «есть ли данные»**, чтобы специалист видел, кто реально
  подключён и кормит кабинет, а кто завис без PRO.

Практические доработки канала 1 (UI, не блокеры): реф-ссылка `?ref=<ref_code>` с запоминанием
кода и авто-подстановкой в экран согласия; блок «Моя ссылка для приглашения» в кабинете
(ссылка + QR + копировать + шаблон сообщения на языке пациента); индикатор PRO на карточке.

### Открытые вопросы онлайн-модели

- **Доход специалиста за ведение:** по умолчанию — напрямую с пациента, мимо нас (как офлайн).
  Альтернатива — ведение тоже через нас с комиссией (тогда нужен платёжный посредник, выплаты,
  возвраты, KYC — тяжёлая ветка). **По умолчанию берём лёгкую (мимо нас), пока владелец не решит иначе.**
- **Путь PRO:** IAP в приложении или код с сайта (наследует открытый вопрос `MOBILE-APP-MODEL.md`).
- **Воронка основателя: бандл vs care-only (чтобы не платить за PRO дважды).** EX/EL у основателя
  на сайте (Hotmart) = «PRO + ведение» одним товаром; клиент без приложения получает доступ **по
  коду → PWA/нативный app** (минуя App Store), всё настроено. **Но** если клиент **уже на PRO**
  (купил через App Store IAP), он ничего не переустанавливает — EX/EL это не отдельное приложение,
  а тот же PRO + ведение. Тогда продавать ему полный бандл значит брать за PRO второй раз. Развилка:
  у основателя нужна **care-only цена** (только ведение) для уже-PRO-клиента, который привязывается
  по `?ref`-ссылке как любой PRO-клиент (основатель = специалист №1) и платит только за
  сопровождение — т.е. тот же случай, что у С Мира. Бандл-через-код остаётся для пришедших **с сайта
  без приложения**. Подтвердить: заводим ли отдельный care-only продукт у основателя.
- **Регуляторика:** удалённое ведение «по миру» + медданные через границы — проверить при росте.
- **Юридические документы (к юристу ЕС — медданные = GDPR ст. 9, особая категория).** Три слоя,
  «по каждому пациенту НИЧЕГО не подписываем» — там только галочка-согласие (уже есть):
  1. *Пациент ↔ специалист:* согласие на данные ✅ (галочка GDPR в анкете); отдельно — договор/
     информированное согласие на саму консультацию = **ответственность специалиста** (его профессия/
     страна); мы можем дать шаблон, но это держит нас «инструментом», не медорганизацией.
  2. *Пациент ↔ мы:* при покупке PRO — Условия использования + Политика конфиденциальности
     (явно: данные передаются выбранному специалисту). Click-accept.
  3. *Мы ↔ специалист:* договор доступа к платформе (условия аренды) + **DPA** (соглашение об
     обработке данных). Роли: специалист = контролёр, мы = обработчик. Подписывается **один раз
     при подключении** (click-accept на первом входе), не по пациентам.
  Минимум к запуску: согласие пациента (есть) + Privacy/ToS для пациента + договор платформы с DPA
  для специалиста + вычитка юристом ЕС.
