# Кабинет нутрициолога — модель (спецификация под реализацию)

> Статус: **дизайн согласован с владельцем (2026-06-05)**, код ещё НЕ менялся.
> Цель — превратить кабинет из прототипа в полноценное рабочее место специалиста
> («1С, только лёгкое»): все данные клиента разбираются в кабинете, а не в ТГ/ботах.
> Источник правды = **кабинет**; Telegram остаётся слоем уведомлений.
>
> Текущее состояние: [`cabinet/index.html`](../cabinet/index.html) (844 стр.) — прототип,
> пароль зашит в исходник (`ADMIN_PASS='VIAL2024'`, публичен на GitHub Pages),
> клиенты в `localStorage` одного браузера. К реальным данным НЕ подключён.

---

## 1. Принцип и две дыры, которые чиним заодно

- **Хранение:** сейчас `localStorage` → потеря при смене устройства. Решение — настоящая БД.
- **Авторизация:** пароль в HTML = публичен. Решение — проверка в воркере (`/cabinet-auth`).

## 2. Как клиент попадает в базу

Карточка «рождается» на **самом раннем сигнале** = **оплата** (Hotmart webhook): тогда уже
известны почта, продукт, тариф, язык. Дальше всё привязывается к **коду доступа** — это
уникальный ключ клиента, который УЖЕ связывает анкету и ТГ-топик (см. ARCHITECTURE §18.11).

Цепочка: **оплата → карточка (по коду)** → клиенту письмо/анкета → когда приходит анкета или
первые данные ИП, в ТГ создаётся **топик** (с тем же кодом) и эти же данные **одновременно**
пишутся в карточку. Топик и карточка появляются вместе — общий код-ключ.

**В базу попадают только оплаченные:** сайт-ведение (Разовая/8/12) + ИП EXPERT/ELITE.
**НЕ попадают:** VIO (бесплатный), PRO (платный, но только ИП+ИИ, без ведения/консультаций).

### Производное поле — «формат сопровождения» (главная развилка работы специалиста)
- **Zoom-формат** (uk/ru ведение/ELITE) → планировать N встреч каждые 7 дн.
- **PDF-формат** (остальные языки) → готовить PDF на почту каждые 7 дн.
- **EXPERT** → 2 PDF за 30 дней (без ведения/Zoom).
- **Разовая** → один Zoom, без продолжения.

## 4. Карточка клиента (структура)

### Профиль (шапка)
Код · Имя · Контакт (почта/ТГ) · Язык · **Продукт** · **Программа** (для сайта) · **Тариф** ·
Длительность · Цена · **Формат** (Zoom×N / PDF q7d / PDF 2 за 30 дн) · Дата старта ·
Дата окончания (расчёт) · Статус (активен / завершён / пауза).

### Вкладки (досье во времени — у каждой записи есть дата)
1. **Анкета** — ответы из `book/anketa` + ИИ-сводка (RU).
2. **Биометрия** — данные с кольца/часов **таблицей по неделям** (срезы: сон, пульс, HRV,
   шаги, вес…). Формат «неделя 1 / 4 / 8» — видно динамику «было → стало».
3. **Разборы ИИ** — список PDF/разборов по датам (прогресс рекомендаций).
4. **Сессии / PDF** — расписание точек (план vs факт): Zoom-ссылки/заметки или отправленные
   PDF, статус каждой (предстоит / проведена).
5. **План / назначения** — рекомендации специалиста.
6. **Переписка** — сообщения клиент↔бот; **ИИ-черновики ответов на утверждение** (см. §6).

### Авто-расписание (ключевая механика динамики и напоминаний)
Из **даты старта + каденс (7 дней) + число точек (N)** кабинет САМ строит список вех
(даты всех сессий/PDF). Это разом даёт: напоминания клиенту, колонки «неделя 1/4/8»,
и контроль «где мы в программе».

## 5. Управление ботом из кабинета

- **Напоминания/рассылки клиенту** — бот ведения уже умеет писать (`/anketa`, `/zoom`,
  авто-сообщения). Добавить «по расписанию» (напр. раз в неделю «пришли самочувствие»).
- **ИИ-черновик ответа → утверждение специалистом** — расширение УЖЕ работающего паттерна
  PDF-разборов (`EXPERT_DRAFTS`: черновик → правка → «отправить»). Клиент написал → ИИ собрал
  черновик ответа (в нутри-рамке, без лекарств/диагнозов — уже в промпте) → специалист в
  кабинете правит и утверждает → ушло клиенту.

## 6. Техническая основа (просто)

- **Хранилище:** Cloudflare **D1** (лёгкая SQL-БД на том же аккаунте; биндится в воркер как KV;
  бесплатного тира хватает; поддерживает список/поиск/пагинацию — то, чего KV не умеет).
- **Бэкенд:** воркер, маршруты `/cabinet/*` (список клиентов, карточка, заметки, отправка,
  утверждение черновика).
- **Вход:** `/cabinet-auth` — пароль проверяется в воркере (НЕ в HTML), выдаётся сессия-токен,
  rate-limit.
- **Ингест:** обработчики `deliverAnketa`, разборов, носимых (`WEARABLE_TOKENS`), Cal-броней
  пишут в D1 **параллельно** с ТГ. ТГ-сообщения остаются как уведомления.

Существующие источники данных: KV `EXPERT_DRAFTS` (переписка/разборы, `care_client:<topic>`,
`code_topic:<код>`), KV `PROGRAM_INTAKES` (`intake:<token>` — анкеты программ), KV
`WEARABLE_TOKENS`, ТГ-канал, Cal.com.

## 7. Этапы внедрения (каждый — рабочий и тестируемый на живом)

1. **Фундамент** (закрывает обе дыры): схема D1 (clients + связанные таблицы) + `/cabinet-auth`
   + кабинет читает реальных клиентов из D1. Миграция текущего `localStorage`.
2. **Ингест анкет:** `deliverAnketa` пишет клиента+анкету в D1 → вкладка «Анкета» показывает данные.
3. **Биометрия (таблица недель) + разборы ИИ + сессии/план** (вкладки карточки).
4. **Переписка + ИИ-черновик→утверждение** (расширить `EXPERT_DRAFTS`) + рассылки по расписанию.
5. **Поиск / пагинация / бейджи статуса / мобайл.**

## 8. Открытые вопросы (подтвердить в реализации)

- Цена ИП **EXPERT**: €120 или €129? (в исходном сообщении было €129, как у разовой, которую
  исправили на €120 → предполагаем €120).
- Набор **статусов** клиента (активен / завершён / пауза / просрочен?).
- Нужен ли учёт **оплат/продлений** (история платежей) в карточке, или только текущий тариф.
- **Хранение PDF-разборов** — ссылка/файл в карточке или только факт отправки.
