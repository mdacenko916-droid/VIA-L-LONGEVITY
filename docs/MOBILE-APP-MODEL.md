# Мобильное приложение ИП (iOS + Android) — модель · слепок 1

> Статус: **черновик-замысел (2026-06-06).** Код не менялся. Это первая фиксация направления —
> «слепок 1». Приложение строим ПОСЛЕ платформы-кабинета ([`PLATFORM-MODEL.md`](PLATFORM-MODEL.md)),
> на её основе (логин, аккаунты, данные уже будут).
>
> Принцип: **переиспользуем готовый веб-ИП, не переписываем с нуля.**

---

## 0. Замысел

ИП становится нативным приложением в **App Store** и **Google Play**. Главная нативная польза
(и причина, по которой Apple одобрит, а не отклонит как «завёрнутый сайт»): приложение читает
носимые устройства **напрямую** — HealthKit на iOS, Health Connect на Android. То есть это не
сайт в рамке, а «гаджет-ридер»: данные с кольца/часов сразу в ИП + push-напоминания в телефоне.

---

## 1. Одно приложение для ВСЕХ тарифов (ключевой принцип)

Приложение — это сам Интерпретатор, **не «приложение только для PRO».** Все тарифы
(VIO/PRO/EXPERT/ELITE) используют один и тот же ИП; тариф лишь задаёт глубину внутри.

- **Скачивание — бесплатное для всех** (оба магазина).
- **Вход — по коду доступа** (та же система, что уже работает: `code_owner` / `code_topic`).
- Тариф привязан к аккаунту/коду и открывает нужный уровень.

→ Отсюда ответ на вопрос «как EXPERT/ELITE-клиент получит приложение»: он скачивает то же
бесплатное приложение и входит по коду, который пришёл ему в письме-подтверждении после оплаты
на Hotmart (механика кода уже есть — `interpreter/ARCHITECTURE.md` §18.11).

---

## 2. Дистрибуция и оплата (где что покупается)

Главное ограничение магазинов: **цифровую подписку, продаваемую ВНУТРИ приложения, обязаны
проводить через встроенную кассу Apple/Google (комиссия 15–30%).** Внешнюю оплату (Hotmart)
внутри приложения для подписки рекламировать нельзя (правило anti-steering). На САЙТЕ —
ограничений нет, кнопки роутим как угодно.

Отсюда чистое разделение:

| Тариф | Где платят | Как попадает в приложение |
|---|---|---|
| **PRO** (масс-подписка, самообслуживание) | встроенная касса App Store/Google Play (IAP) — самый гладкий путь для мобильного клиента; комиссия ~15% (small business) | подписался прямо в приложении → доступ открылся |
| **EXPERT / ELITE** (воронка основателя) | **Hotmart на сайте** — 0% комиссии магазинам | оплата → код в письме → скачал бесплатное приложение → вошёл по коду |
| Абонплата **специалиста** (B2B) | на сайте (Hotmart/иное) | специалист входит в кабинет, не через клиентский app |

**Что внутри приложения, чтобы не нарушить правила Apple:**
- предложить только **PRO (через IAP)** и поле **«ввести код доступа»** (для оплативших на сайте);
- **полную таблицу тарифов с ссылками на Hotmart показываем ТОЛЬКО на сайте**, не в приложении.

Сайтовая страница тарифов (вопрос владельца) — разделять МОЖНО и нужно: PRO → магазины/IAP;
EXPERT/ELITE → Hotmart. Сайт под правила in-app не попадает.

## 3. Технический путь (переиспользуем готовое)

1. **Обёртка Capacitor** над существующим веб-ИП — весь HTML/CSS/JS/логика переиспользуются,
   бэкенд остаётся тот же (Cloudflare Worker).
2. **Нативные мосты:** чтение здоровья (HealthKit / Health Connect) → в общий каркас носимых
   (`WEARABLE_TOKENS`, `connectWearable`/`fetchWearableLive`); push-уведомления (напоминалка
   теперь и в телефоне, не только ТГ/почта).
3. **IAP** для PRO (если выбираем in-app подписку) — плагин покупок Capacitor + проверка чека
   на воркере → активация кода/тарифа.

---

## 3.1 Чтение «склада здоровья» + добор недостающего (продуктовое требование)

Это **главный нативный смысл** приложения и универсальный путь ко всем гаджетам.
Подробная карта «кто отдаёт в склад» — [`interpreter/wearables/app-health-store.md`](../interpreter/wearables/app-health-store.md).

**Зачем:** почти все 11 устройств сами пишут данные в Apple Health (iOS) / Health Connect
(Android) — Oura, Garmin, Polar, Withings, Ultrahuman, Amazfit, Xiaomi, Apple Watch, Fitbit,
WHOOP, Samsung (Android). Приложение читает склад **одной интеграцией, без кодов разработчика
и без партнёрских заявок** по каждому вендору. Любой новый гаджет, пишущий в склад,
подхватывается автоматически — карточку под него заводить не нужно (закрывает «длинный хвост»).

**Логика приложения (требование):**
1. Подтянуть всё доступное из склада здоровья.
2. Сверить с показателями, которые нужны разбору ИП.
3. Увидеть, чего не хватает — почти всегда это **HRV** (в склад не шлётся или в других
   единицах: Apple = SDNN, кольца/ремни = RMSSD), иногда фирменные «оценки»
   (готовность Oura, recovery WHOOP, темп. отклонение). Сам HRV из склада мост
   (`interpreter/healthkit-bridge.js`) с 2026-06-12 берёт как **ночное среднее SDNN в окне сна**
   (а не последний сэмпл за сутки) — ближе к ночной HRV кольца, но это всё ещё SDNN, не RMSSD;
   полное совпадение с экраном Oura даёт только прямой Oura API (`interpreter/wearables/oura.md`).
4. **Мягко попросить клиента дописать вручную ТОЛЬКО недостающее** — не весь список, а 1–2
   пробела. (Тёплый тон, как везде в боте — см. memory `project_vial_care_value`.)
5. Если позже придумаем добор HRV без рук (через API устройства или иначе) — заменим ручной шаг.

**Условие:** у клиента должно стоять «родное» приложение бренда + включён обмен со складом
(данные идут «устройство → приложение бренда → склад → наш апп»). Один раз включить.

## 3.2 AI-анализ и недельный разбор (наследуются от веб-ИП)

Приложение — Capacitor-обёртка веб-ИП, поэтому **весь AI-функционал работает «из коробки»**,
отдельной нативной реализации не требует:
- **Подневный AI-анализ** — каждый прогон ИП шлёт данные на воркер `/analyze`, ответ рендерится
  в карточке результата (механика — `interpreter/ARCHITECTURE.md` §4.5).
- **Недельный AI-разбор** (с 2026-06-12) — связный разбор динамики за неделю, **1 раз в 7 дней**
  (гейт на localStorage; смысл — увидеть картину изменений, а не дневной шум). Воркер
  `/weekly-report`, клиентский блок под «Динамикой недели». В EXPERT/ELITE тот же разбор уходит
  специалисту в кабинет. Механика — `interpreter/ARCHITECTURE.md` §4.8 + §5.7.

В приложении это особенно ценно: нативный добор HRV/сна из склада (§3.1) → подневный разбор →
накопленная за неделю история → недельный разбор. Никаких доп. экранов под app писать не нужно.

## 4. Практика (факты)

- Apple Developer Program — **$99/год**; Google Play Developer — **$25 один раз**.
- Проверка App Store строгая (дни–недели), Google Play мягче.
- Комиссии: Apple/Google 30%, но **15%** по программе для малого бизнеса (<$1M/год) и для
  подписок. EXPERT/ELITE через Hotmart комиссии магазинам не платят вовсе.

## 5. Этапы (после платформы-кабинета)

0. **Слепок 1 (этот документ)** — зафиксировать направление.
1. Платформа-кабинет (Шаги 1–6 из `PLATFORM-MODEL.md`) — фундамент: аккаунты, логин, данные.
2. Capacitor-обёртка веб-ИП → сборки iOS/Android, запуск в эмуляторе.
3. Нативное чтение здоровья (HealthKit / Health Connect) + push. Включает добор недостающего:
   подтянуть из склада → найти пробелы (в первую очередь HRV) → попросить дописать только их (§3.1).
4. Вход по коду доступа в приложении.
5. (Если решим) IAP для PRO; иначе PRO тоже по коду с сайта.
6. Публикация: аккаунты разработчика, листинги, ревью, релиз.

## 6. Открытые вопросы

- **PRO в приложении:** продавать через IAP (гладко, ~15%) ИЛИ только вход по коду с сайта
  (0%, но Apple может придраться к «приложению только для входа»)?
- Минимальный набор нативного, достаточный для одобрения Apple (HealthKit + push — вероятно да).
- Нужен ли отдельный **кабинет специалиста в приложении**, или специалисты работают только из
  веб-кабинета, а app — клиентский.
- Бренд/иконка/название в сторах, политика конфиденциальности (обязательна для обоих магазинов).
